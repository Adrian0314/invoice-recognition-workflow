# 发票识别工作流 · Invoice Recognition Workflow

把发票文件（PDF / 图片）丢进文件夹，自动识别关键字段、写入 Excel 台账并输出异常报告。
同一个问题在本仓库有**两套实现**，业务语义同源、结果可交叉验证：

| 实现 | 位置 | 适用场景 |
|---|---|---|
| **纯 Python 单文件版（推荐上手）** | [`optimized_python/`](optimized_python/) | 零依赖、IDLE 按 F5 即跑；个人 / 小团队 / 离线环境 |
| **UiPath 工作流版** | [`optimized_uipath/`](optimized_uipath/) | 生产级运行治理、人工回环、多机器人扩容 |
| 原方案（v1） | [`invoice_wf/`](invoice_wf/) + `main.py` / `watch.py` | 本 README 下半部分即 v1 的设计记录 |

> 📖 **建议先读**：[优化说明与方案对比.md](优化说明与方案对比.md)
> —— 调研了 GitHub 上三类主流做法（纯 Python 模板库 / OCR+LLM 混合 / RPA+CI），
> 逐项说明九项改进「改了什么、为什么、实测效果」，并对比两版的适用场景与优劣。

```bat

:: 把发票放进 invoices_input\ 后处理（无需安装任何第三方包）

```

# 发票自动化处理工作流

把发票文件（PDF / 图片）丢进文件夹，自动识别关键字段、写入 Excel 台账并输出异常报告。
**一个文件一张发票一行**，支持批量处理、重复校验与异常提示。

```
发票文件(PDF/图片)
      │
      ├─ 1. 扫描目录            discover_files
      ├─ 2. 文件指纹去重        sha256 前 16 位
      ├─ 3. 文本提取            PDF 文本层 → 无文本层则 OCR
      ├─ 4. 字段解析            号码/日期/金额/税额/购销双方/税号/税率/明细
      ├─ 5. 规则校验            13 项财务级校验，分级 严重/警告/提示
      ├─ 6. 发票级重复校验      发票代码+号码 唯一
      └─ 7. 输出               Excel台账 + HTML报告 + CSV/JSON + 异常清单
```

## 一、快速开始

```bash
# 1) 安装依赖（已内置独立虚拟环境，见下方说明）
pip install -r requirements.txt

# 2) 生成一批演示发票（可选，用来验证流程是否跑通）
python make_samples.py

# 3) 把发票放进 invoices_input/，然后执行
python main.py
```

产物全部在 `output/`：

| 文件 | 说明 |
|---|---|
| `发票台账.xlsx` | **主台账**，3 个 sheet：发票明细 / 异常记录 / 汇总统计 |
| `处理报告.html` | 可视化报告，含 KPI 卡片、异常清单、明细表，可直接打印归档 |
| `发票明细.csv` / `.json` | 结构化导出，便于导入财务系统 |
| `异常记录.csv` | 异常清单单独导出 |

> **CSV 里的发票代码 / 发票号码 / 税号按文本导出**：这些是纯数字长串，直接按数字写的话，
> 用 Excel 打开会丢前导 0（`011002000001` → `11002000001`）、20 位号码还会变成 `2.4312E+19`。
> 所以导出时写成 Excel 的文本写法 `="011002000001"`，打开后显示完整 12 位。
> 这是**有意的**：用别的程序读 CSV 时，要么用 `invoice_wf.csv_util.parse_cell()` 反解，
> 要么直接读 `发票明细.json`（那边是原始值）。
> 另注：不能图省事改用 `csv.writer` —— 它会把字段里的引号再转义一层，
> 落盘成 `"=""011002000001"""`，Excel 反而会把 `="…"` 当普通文字显示出来。

> 依赖：`pip install -r requirements.txt`（v1 需要 PyMuPDF + openpyxl；v2 单文件版零依赖即可运行）。

> **⚠ 维护 `run.bat` 时注意**：该文件必须是 **GBK(ANSI) 编码 + CRLF 换行**，这是 cmd.exe 的硬性要求。
> 若被编辑器以 UTF-8 重新保存，会出现乱码，甚至报
> `'C:\Windows\System32\cmd.exe' 不是内部或外部命令，也不是可运行的程序或批处理文件` 这类莫名错误。
> 修改后请用记事本「另存为 → 编码选 ANSI」，或执行 `python make_run_bat.py` 重新生成。
> 只改 `.py` 文件不受影响。

## 三、识别字段（= Excel 台账的列）

| 列 | 说明 |
|---|---|
| 序号 / 源文件名 / 处理时间 | 溯源信息 |
| 发票类型 | 数电发票(普通/专用)、电子普通/专用发票、增值税专用/普通发票… |
| 发票代码 / 发票号码 | 真实票据：数电票无发票代码（20 位号码）；老版为 12 位代码 + 8 位号码。本仓库样本为覆盖该字段，两类都填了 12 位代码（见第九节） |
| 开票日期 | 统一输出 `YYYY-MM-DD` |
| 购买方名称 / 购买方税号 | 含「统一社会信用代码」自动识别 |
| 销售方名称 / 销售方税号 | 同上 |
| 金额(不含税) / 税额 / 价税合计 | 数值型，千分位格式；缺失项会用「价税合计 − 税额」自动推导 |
| 税率/征收率 | 多税率会自动合并，如 `6%/13%`；支持 免税、不征税 |
| 主要项目/货物名称 | 取 `*类别*名称` 形式的明细行 |
| 校验码 / 开票人 | 老版电子发票的校验码、开票人姓名 |
| 处理状态 | 正常 / 存在提示 / 异常 / 待人工录入 |
| 异常/提示说明 | 该行所有问题的摘要 |
| 文件指纹 | 隐藏列，用于「同一文件重复提交」判定 |

## 四、校验规则（13 项）

**严重**（数据不可直接用）
1. 必填字段缺失：发票号码 / 开票日期 / 价税合计 / 购销双方名称
2. 发票号码含非数字字符
3. 开票日期非法或**晚于当前日期**
4. **金额勾稽不平**：`金额(不含税) + 税额 ≠ 价税合计`（容差 0.02）
5. 税号格式非法

**警告**
6. 发票号码位数与版式不符（数电票应为 20 位）
7. 开票日期过早（< 2000 年）
8. 税号长度异常（常见 15/17/18/20 位）
9. **统一社会信用代码校验位不通过**（GB 32100-2015 真实算法，可捕捉 0/O、1/I 类识别错误）
10. **购买方与销售方名称完全相同**（自查自开）
11. 价税合计为 0
12. 销售方税号缺失
13. 非数电发票缺少发票代码

**提示**
14. 红字发票（金额为负，提醒冲减方向）
15. 税率不在常用集合内

**重复校验**（两级）
- **发票级重复**：发票代码 + 发票号码 已存在于台账 → 阻止重复入账
- **文件级重复**：文件内容 sha256 指纹相同 → 阻止重复入账
- 同一目录反复扫描属正常幂等，静默跳过不计入异常；只有**换文件名再次提交**才登记为「重复提交」

## 五、OCR（图片 / 扫描件）

电子版 PDF 发票自带文本层，识别准确率 100%，**无需 OCR**。
只有图片（JPG/PNG）和扫描件 PDF 需要 OCR：

```bash
pip install rapidocr "onnxruntime==1.20.1"     # 推荐：纯 pip、免编译
pip install paddleocr paddlepaddle             # 备选：准确率略高，但老 Python/Windows 上极难装成
pip install pytesseract                        # 备选：需另装 Tesseract-OCR 主程序 + chi_sim 语言包
```

引擎按 **RapidOCR → PaddleOCR → Tesseract** 优先级自动探测。

装好后执行 `python main.py --retry-failed`，即可自动补全此前标记为「待人工录入」的记录。
未安装时不会静默丢数据 —— 文件仍会被登记为一行「待人工录入」并写入异常清单。

> **onnxruntime 版本坑**：onnxruntime 1.30 在 Windows 10.0.17763 上 `import` 即访问违例
> （原生崩溃，非 Python 异常），实测 **1.20.1 可用**。
> 因此 OCR 被放在**独立子进程**（`invoice_wf/ocr_worker.py`）里执行：
> 引擎崩溃只影响当前那一个文件，整批任务不会失败。
> 详见 `使用手册.md` 第 9 节。

## 八、设计要点

- **Excel 就是唯一数据源**：每批处理先读回台账建立索引，再增量追加。人工改过的单元格不会被覆盖。
- **绝不静默丢数据**：任何无法识别的文件都会产生一行「待人工录入」+ 一条异常记录。
- **单文件失败不中断整批**：异常被降级为记录，流程继续。
- **原生库崩溃也打不垮批次**：OCR 跑在独立子进程里，引擎挂了只影响当前文件。
- **反复跑不会污染台账**：问题记录带去重指纹，金额合计只统计真正入账的行；
  文件成功识别后还会自动清掉它此前「提取失败」类的失效记录。
- **文本粘连容错**：PDF 抽取常把各列粘成 `11000.001000.006%`，解析层用「金额固定两位小数」这一特征逐段剥离，准确取出税率。

## 九、国际商务发票样本（make_intl_samples.py）

### 来源核查结论：目标站点不提供任何可下载模板

对 `https://www.realguts.com.tw/invoice` 做过完整核查，结论是**下载到的模板数 = 0**：

| 核查项 | 结果 |
|---|---|
| 首页列出的模板条目 | 6 个（缩略图 + 详情页链接），**无任何 `.psd/.docx/.pdf/.zip` 文件链接**，无分页 |
| 详情页正文 | 通用介绍文案；两次抓取除 H1 标题外**逐字一致**，无模板独有内容 |
| "模板下载"链接 | 只有一个，href 为占位符 `#` |
| 页面声称 | 提供 Word(.docx) 与 PDF 文件 —— 但页面上不存在任何真实文件 URL |
| 本机直连 | `realguts.com.tw` 的 HTTPS 被 TLS 重置（Python 与 PowerShell 均如此），二进制文件也无法获取 |

**判定：该站是 SEO 内容页，没有可下载的模板文件。** 因此 `make_intl_samples.py`
不含任何下载内容，而是依据该站点**自己列出的 6 个模板类型**、以及其在页面中明确描述的
字段结构（公司 Logo 区、客户信息、发票编号、开票日期、付款方式、商品清单、单价、数量、税额、总金额），
重建等效版式后生成样本。版式为重建，非复制。

### 生成的样本

6 种版式 × 每种 2 份 = **12 份**，命名 `T<模板号>-<序号>_<模板中文名>_<业务场景>.pdf`：

| 模板号 | 版式 | 关键差异 | 样本 |
|---|---|---|---|
| T1 | 专业发票 INVOICE | 标准条目式 + 签章区 | 软件开发服务 / 设备采购 |
| T2 | 代理发票 AGENCY INVOICE | 含代理费与垫付款行 | 代理服务费 / 佣金结算 |
| T3 | 估算发票 ESTIMATE | 顶部「非付款凭证」色带，无签章 | 项目预估价 / 季度预算估算 |
| T4 | 条款发票 WITH TERMS | 底部三段条款正文 | 年度维保 / 物流服务 |
| T5 | 简式发票 SIMPLIFIED | 无 Logo、单条目、最简结构 | 办公用品 / 翻译服务 |
| T6 | 演讲者发票 SPEAKER | 含演讲人/主题/时间地点区块 | 主题演讲 / 培训课程 |

**关键字段全部唯一**：文件名、发票编号、开票日期、小计、税额、总金额各 12 种取值，无重复；
每份金额满足 `小计 + 税额 = 总金额`（税额按各自税率 5%/6% 计算）。明细见 `samples_intl/样本清单.csv`。

**文字一律简体中文**：公司名、地址、银行、联系人、演讲信息等全部为简体
（早期版本按台湾站点的模板类型写成繁体，已统一改为简体）。

**生成物声明**：公司名、人名、税号、银行账号均为虚构；发票编号内含 `SAMPLE` 标识；
页脚固定标注「软件测试用虚拟样本…不具票据效力」。仅供测试与教学使用。

### 发票代码 / 发票号码：按官方编码规则生成

规则集中在 `invoice_wf/code_rules.py`，三套生成器共用，不再各处各写一份：

| 字段 | 位数 | 结构 | 依据 |
|---|---|---|---|
| 发票代码 | 12 位 | `0` + 地区(4) + 年度(2) + 批次(3) + 票种(2)，票种 `11`=电子普票、`13`=电子专票 | 总局公告 2020 年第 22 号、2017 年第 44 号 |
| 发票号码（数电票） | 20 位 | 年份后两位(2) + 省级区域码(2) + 开具渠道(1) + 15 位顺序码 | 总局公告 2024 年第 11 号 |
| 发票号码（老版电子票） | 8 位 | 按年度、分批次编制 | 同 2020 年第 22 号 |

- 地区码取全国行政区划的地市级 4 位码：上海 `3100`、深圳 `4403`、厦门 `3502`、
  重庆 `5000`；本项目的销售方在中国台湾，取台湾省 `7100`（行政区划代码 710000）。
- 年度与号码前两位都取**开票日期的年份**，与票面日期一致，不会出现"号是 2024、票是 2026"。
- 为了让每个样本的代码都唯一、便于逐份核对，**批次位按票递增**；
  真实场景中同一批次的发票共用同一个代码、靠发票号码区分。
- ⚠ **数电票（20 位号码）本身不带发票代码**。本项目为了让样本覆盖该字段，
  **给全部样本都填了 12 位代码**，这偏离真实规范 —— 若要还原真实形态，
  把 `make_samples.py` / `make_intl_samples.py` 里的 `invoice_code` 置空即可。

### 与现有解析器的兼容性（已修复）

初版这 12 份用的是纯国际版式（`Invoice No. / Bill To / Subtotal / Total Due`），
与 `parser.py` 实现的中国大陆发票字段规则不匹配 → 12 份全部判为「异常」。**现已修复**：

在**不改版式、不改文件名**的前提下，把原有的各区块标签补成解析器可识别的写法，
并补齐票面要素（20 位发票号码、12 位发票代码、购销双方 18 位税号），
同时把「合计金额 / 合计税额 / 价税合计」的金额口径对齐（附加项并入明细行）。

修复后实测：**12 份全部「正常」，0 异常**。

> **改标签时踩到的 3 条边界规则**（做同类适配时会反复遇到，务必遵守）：
>
> 1. **中文标签必须紧贴取值**，中间不能夹英文或冒号。
>    解析器用的是「标签 + 可选冒号 + 取值」模式，所以英文只能写在中文**之前**
>    （`Invoice No. / 发票号码` ✅，`发票号码 / Invoice No.` ❌）。
> 2. **名称字段后面必须紧跟一个终止词**。名称的取值靠
>    `(?=销售方|购买方|纳税人识别号|…)` 前瞻截断，所以税号标签要写成纯中文
>    「纳税人识别号」——写成 `Tax ID / 纳税人识别号` 会把 `TaxID/` 一起并进名称里。
> 3. **税号取值后面不能紧跟字母或数字**。税号用 `[0-9A-Z]{15,20}` 贪婪匹配，
>    后面若跟着 `Address` 这类以字母开头的标签，会把首字母 `A` 吃进去变成 19 位。
>    紧跟的标签必须以**中文**开头（如 `地址 / Address`、`备注 / Remarks`）。

另：购销双方的税号用了中国大陆统一社会信用代码格式（18 位、校验位正确），以满足校验规则。
真实台湾地区公司用的是 8 位「统一编号」，若要还原真实格式，需放宽 `validator.py` 里的税号格式规则。

### 重新生成

```bat
python make_intl_samples.py
```

> ⚠ **重新生成样本后，要先清空 `output/` 再重跑 `main.py`。**
> 原因是 PDF 每次生成时内部的隐藏文档 ID 都不同 —— 内容一样、字节不一样，
> 于是同一个发票号码会被台账判为「发票级重复」，问题清单凭空多出十几条。
> 正确顺序：删掉 `output/发票台账.xlsx` → 重跑 `main.py`。真实发票不会遇到这个问题
> （原件字节是固定的），只有重新生成合成样本时才会。

顺带记录两个踩过的排版坑（改这个生成器时会遇到）：

1. **不要用 PyMuPDF 内置的 `china-s` 字体做对齐排版**：它的宽度度量把拉丁字符也当全宽（1em）处理，
   而实际渲染是按比例的 —— 于是 `insert_textbox` 会误判「放不下」并**静默丢弃整段文字**（金额凭空消失），
   `get_text_length` 也会偏大导致右对齐错位。改用系统真实字体（本机用 `Deng.ttf`）。
2. **嵌入真实中文字体必须做子集化**：完整嵌入一个中文字体，单份 PDF 会涨到 5~15MB、保存耗时十几秒
   （表现为"卡住"）。调用 `doc.subset_fonts()` 后降到 25KB 上下。注意 PyMuPDF 自带该能力，无需 fontTools。

`invoices_input/` 是**可再生的临时收件箱**，权威副本在 `samples/` 与 `samples_intl/`。

python make_samples.py            :: 重新生成 10 份中文增值税样本并复制进收件箱

## 十一、reportlab 样票生成器与异常修复记录

### 两个生成器

| 脚本 | 产物 | 说明 |
|---|---|---|
| `generate_mock_pdf.py` | `虚拟IT公司样票_10张.pdf` | 用户提供的**原始脚本**，保持原样未改动 |
| `generate_mock_pdf_fixed.py` | 同名文件 | **修正版**：修渲染缺陷 + 补发票要素字段 |
| `samples_mock/虚拟IT公司样票_10张_原始版.pdf` | — | 修正版覆盖前的原始产物备份 |

### 原脚本自带的两个渲染缺陷（修正版已解决）

1. **裸字符串单元格不继承自定义字体**。reportlab 的 `Table` 里直接放 `"项"` 这类字符串，
   会用默认 Helvetica 绘制 → 中文渲染成黑色方块（notdef）。
   必须用 `Paragraph(text, style)` 包一层。
2. **裸字符串单元格不解析 `<b>` 标记**。`"<b>合计</b>"` 会**原样打印**成字面 `<b>合计</b>`。
   粗体必须写进 `Paragraph`，并且要 `registerFontFamily(...)` 注册 bold 面才生效。

### 修正版新增的 5 个坑（都已处理）

- **`¥` 不能放进 `<b>` 里**：加粗面用的 SimHei 没有 U+00A5 字形，会渲染成空方块。
  写法改成 `f"¥<b>{n:,.2f}</b>"`，让 `¥` 走常规字体。
- **`random.seed()` 未固定种子**：每次运行金额都不同，但发票号码是按序生成的、
  两次运行会**完全相同** → 重跑会被判为「发票级重复」。
  建议改成 `random.seed(20260918)` 让样本可复现。
- 10 页 PDF 原先被当成 **1 条记录**（切分靠「发票号码」锚点，而原文用的是「样票编号」）；
  补上逐页唯一的「发票号码」后，正确拆成 **10 条记录**。

### 一次修复的完整对照

| 文件族 | 修复前异常 | 修复后异常 | 处理方式 |
|---|---|---|---|
| 国际商务样本 T*（12 份） | 72 条 | **0** | 标签改为可识别写法 + 补票面要素 + 对齐金额口径 |
| reportlab 样票（10 页） | 6 条 | **0** | 修正渲染缺陷 + 补票面要素 + 引入 6% 税率 |
